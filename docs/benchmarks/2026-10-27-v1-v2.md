# 2026-10-27：LZMA V1 与定宽差分/ZigZag V2

本文保留原始 2,301 份样本的历史测量。当前默认样本集已缩减至 1,038 份，
其中 RMV 2 保留 200 份，见[精简样本报告](2026-10-27-v1-v2-reduced.md)。

本报告比较 MSRC 开发版 `0.2.0` 中同时保留的两套算法：

| 算法 | 文件头 `(algorithm_id, algorithm_version)` | 处理方式 |
| --- | --- | --- |
| V1 | `(1, 1)` | 原始字节直接 LZMA1 |
| V2 | `(1, 2)` | 字段分流、定宽时间差分、坐标差分/ZigZag、字节平面分流，再 LZMA1 |

V2 保留原始按键码、状态位、MVF 残余位、非鼠标事件、头尾和签名。
EVF 0.4 现有的 16 位有符号坐标增量，以及 RMV 2 reduced move 的 4 位增量也做 ZigZag，
不重复差分。[载荷规范](../algorithms/lzma-v2.md) 定义具体操作。
V1 和 V2 均保留压缩及解压接口，新版本默认使用 V2。

## 环境与测量方法

- CPU：AMD Ryzen 7 4800H with Radeon Graphics，16 个逻辑处理器。
- 系统：Windows 11，构建号 `10.0.26300`，AMD64。
- Rust：`1.99.1 (58cf8f9c3 2026-10-13)`，`x86_64-pc-windows-msvc`，release 构建。
- 调用方式：CPython `3.14.6` 的 PyO3 绑定，核心编码和解码由 Rust 完成。
- LZMA：`lzma-rust2 0.24.0`，两版均为 preset 6；相同输入长度对应相同字典选取规则。
- 每份文件预热 1 轮，再测量 5 轮；交替 V1/V2 的先后顺序，串行调用。
- 每轮都解压并逐字节比较原文，包括预热。检查失败会记录并以非零状态退出。
- 每份文件分别取压缩、解压耗时的中位数，再按格式求和。吞吐量使用原始字节总量除以
  这些中位数之和，单位 MiB/s（`1 MiB = 1,048,576 B`）。
- 计时包含 Rust 编解码、CRC、预处理/逆变换、Python 绑定调用和返回字节的复制；
  不包含文件 I/O、计时外的 `inspect`、字节比较、CSV/JSON 写入和构建时间。

V2 编码会实际压缩两种候选，比较包含描述开销的完整载荷后选较小者：原始字节路径与
预处理路径。**这两次 LZMA 的耗时都算入 V2 压缩时间**。选择原始路径时仍写算法版本 2，
与显式请求 V1 是不同的文件头。当前编码策略保证同级别 V2 至多比 V1 多 1 B。

## 样本快照

共 **2,301 个物理文件，76,534,627 B 原文**：304 AVF、6 MVF 0.97、222 RMV 1、
1,463 RMV 2、100 EVF 0.3、200 EVF 0.4、6 EVFS 0.0。
RMV 1/2、EVF 0.3/0.4 依据文件头区分，目录名不作为版本判据。

EVFS 内含 298 份 EVF 0.4，但本报告按 6 个完整集合文件计数，V1/V2 都在同一个集合的
全部原始字节上比较。集合内部与独立 EVF 之间可能有重复，未全局去重。
首批 AVF/RMV 1/EVF 使用体积分层取样；MVF 和 RMV 2 是随后提供的集合。
这些是本地样本，既不是随机抽样，也不代表所有玩家或软件版本的分布。

RMV 2 单独分组很重要：它们已有紧凑移动记录，其中 9,854,239 条为 3 B reduced move。
V2 对普通记录与 reduced move 使用不同的定宽操作，并让两者共享鼠标预测基准。

## 结果解释与边界

全部 2,301 份文件在两版、每版 1 次预热和 5 次测量中逐字节恢复一致，共检查 27,612 次压缩/解压对。
V2 总体积从 **22,123,398 B** 降至 **15,041,017 B**，比 V1 减少 **32.01%**；
占原文比例从 **28.91%** 降至 **19.65%**。

压缩耗时的中位数之和为 **26.229 s → 48.196 s**，V2 约为 V1 的 **1.84 倍**。
解压为 **1.322 s → 1.320 s**，整体近似持平，这点差异不足以宣称总体解压更快。
AVF、RMV 1、EVF 0.3 解压更快，RMV 2、EVF 0.4、EVFS 和这 6 份 MVF 的解压吞吐量下降。

V2 在 **2,300/2,301** 份文件中选择了预处理路径；另外 1 份 EVF 0.4 使用原始字节路径。
RMV 2 的 1,463 份样本全部使用专用预处理，体积减少 **32.16%**。

V2 的结果反映整套“分流＋差分/ZigZag＋LZMA＋候选比较”，本次没有逐项消融，
不能将全部体积收益归因于单个步骤。保留候选比较也有明确的压缩耗时成本。
各格式的解压速度变化应分别看表，不能仅依据压缩率推断。

本次没有测量峰值内存，也没有测量浏览器、WASM 或其他平台的性能。
`max_memory_kib` 仅约束 LZMA 工作内存估算，V2 另有输出及一个事件段的临时缓冲区。
机器没有隔离操作系统后台任务；重复与中位数只能减轻噪声，不能消除所有环境影响。
MVF 只有 6 份 0.97 样本，不能外推到 MVF 2006/2007；早期 MVF、EVF 0.0–0.2、RAWVF
以及含棋盘/指标事件的 EVF 0.4 没有对应真实性能组，未知布局会走 V2 原始字节路径。

## 原始聚合数据与复现

[聚合 JSON](2026-10-27-v1-v2.json) 保存精确字节数、中位数耗时之和、环境、参数与源码指纹。
源码指纹由根 Cargo 配置、Python 绑定的 Cargo 配置/入口和 `src/**/*.rs` 计算，
统一 CRLF 为 LF；它不代表完整 Git 提交，也不是已发布版本的声明。
逐文件 SHA-256、各次原始耗时和结果在 `target/algorithm-comparison.csv`，不提交。
报告不包含原始录像、私有文件名或外部录像目录。

激活仓库虚拟环境并从当前源码构建 release 绑定后执行：

```powershell
maturin develop --release --locked
python scripts/compare_algorithms.py --rounds 5 --warmups 1 --level 6 `
  --report target/algorithm-comparison.csv `
  --summary target/algorithm-comparison.json
```

如需核对文件布局，可另运行 `python scripts/inspect_mouse_events.py`。
这两种工具都不修改录像。样本未公开，因此外部用户无法复现完全相同的数据集，
但可使用同一脚本在自己的样本上复现测量方法。后续报告应保留这份历史快照，
用新日期/算法组合追加结果，继续包含旧版本的压缩与解压测试。
