调研日期：2026-10-27。目标是为 **逐字节可逆预处理 + 通用压缩器** 建立依据。
本文描述磁盘上的记录，区分原始编码、解析器提供的语义和本地实测结果。
调研结果已用于 `0.2.0` 的 [V2 定宽差分/ZigZag 算法](../../algorithms/lzma-v2.md)。
MSRC 容器头保持不变，V1 的压缩和解压继续保留；实测结果见 [benchmark](../../benchmarks/README.md)。

## 总览

`uN/iN` 表示 N 位无符号/有符号整数，BE 表示大端；B 表示字节。
`type` 是事件类型，`buttons` 是该时刻按键状态，两者不能互换。
坐标均为像素，除非明确注明为格坐标。

| 格式/版本 | 一条鼠标记录 | 时间 | 坐标 | 按键 |
| --- | --- | --- | --- | --- |
| AVF | 8 B，字段交错 | 绝对秒数 + 百分秒，秒字段存值比时间大 1 | 绝对 `u16 x/y`，字节分散 | 独立事件码，含别名 |
| MVF 0.97 | 5 B，40 位按文件重排 | 10 位秒 + 7 位百分秒 | 9 位 x + 9 位 y | 3 位状态快照 |
| MVF 2006/2007 | 6 B，48 位按文件重排 | 22 位绝对毫秒 | 11 位 x + 11 位 y，存值各加 32 | 3 位状态快照 |
| 早期 MVF | 8 B | 秒字节 + 百分秒字节 | 两个 BE `u16` | 状态字节，另有未解释字节 |
| RMV 1 | 9 B | BE `u24` 绝对毫秒 | BE `u16 x/y`，相对窗口客户区 | 事件码 + `nFlags` |
| RMV 2 普通记录 | 9 B | 同上 | BE `i16 x/y`，相对棋盘 | 事件码 + `nFlags` |
| RMV 2 reduced move | 3 B | `u8 Δt` | 两个有符号 4 位增量 | 沿用上一条的 `nFlags` |
| EVF 0.3 | 8 B | BE `u24` 绝对毫秒 | BE `u16 x/y`，相对棋盘 | 独立事件码 |
| EVF 0.4 | 6 B；可穿插 3 B pause | `u8 Δt`，pause 增补 `u16 Δt` | 两个 BE `i16` 增量 | 独立事件码 |
| EVFS 0.0 | 包含完整 EVF 块 | 由每个内嵌 EVF 决定 | 同左 | 同左 |
| RAWVF | 文本行，变长 | 十进制秒 | 文本格坐标与像素坐标 | 文本事件名 |

## AVF：8 字节交错记录

两套 [Rust][avf-rs] / [C][avf-c] 解析器的字段计算一致。设一条记录是 `b[0..8]`：

| 偏移 | 内容 |
| --- | --- |
| 0 | 事件码 |
| 1 | x 高字节 |
| 2 | 秒数低字节 |
| 3 | x 低字节 |
| 4 | 百分秒 |
| 5 | y 高字节 |
| 6 | 秒数高字节 |
| 7 | y 低字节 |

```text
x = 256*b[1] + b[3]
y = 256*b[5] + b[7]
t_ms = (256*b[6] + b[2] - 1)*1000 + b[4]*10
```

事件码：`1 mv`、`3 lc`、`5 lr`、`9 rc`、`17 rr`、`33 mc`、`65 mr`。
还有 `145 rr`、`193 mr`、`21 lr` 等别名，C 解析器把 `11` 解释成 `sc`
（Shift 点击），Rust 对 `11` 会 panic。压缩时保留原事件码，不能把别名统一。
实测 AVF 就出现了 1 条 `145`，不是只有常见的 7 个码。

结束记录仍占 8 B，秒字段 `b[2] == b[6] == 0`；不能只保存“事件结束”而丢弃其余字节。
之后还有校验/软件版本/皮肤/玩家等尾部内容，全部属于原文件。
事件流前的内容也不是定长头：上游在文本时间头后，滑动查找
`b[2] == 1 && b[1] <= 1` 作为同步启发式。这不是可靠的通用魔数。
新算法应严格验证候选段，失败或版本不识别时回退整文件压缩。

## MVF：按键状态快照和位重排

### Clone 0.97 beta

[Rust][mvf-rs] 和 [C][mvf-c] 均表明，每个文件在事件数之前保存一个 BE `u16` 种子，
据此生成固定的 40 位排列，同一文件的所有 5 B 记录共用该排列。
种子经平方根、sin/cos、乘 `10^8`、舍入生成 40 个十进制字符；按字符值升序、
原位置稳定排序，决定逻辑位对应的原始位。原始字节内的位从最低位开始编号。
事件数是 BE `u24` 的**记录条数**；C 源码将其注释成字节数，但实际循环每次读取 5 B。

解除排列后，逻辑位编号如下；多位字段从低位开始累积：

| 逻辑位 | 内容 |
| --- | --- |
| 0 | 右键状态 |
| 1 | 中键状态 |
| 2 | 左键状态 |
| 3–11 | y，9 位 |
| 12–20 | x，9 位 |
| 21–27 | 百分秒，7 位，乘 10 得毫秒部分 |
| 28–37 | 秒，10 位 |
| 38–39 | 两套解析器都未使用的 2 位，必须保留 |

这里没有单独的 `mv/lc/lr` 事件码。解析器比较前后位置与按键状态，
可以把一条快照展开成多个语义事件，也可以不输出事件。
这种展开不保留原始快照数量，不能直接作为可逆压缩的中间表示。
上游还会改写越界坐标，并根据第一个释放动作调整计时原点。

6 个新增样本共 13,317 条记录，其中 **9,928 条的未解释 2 位非零**。
每个样本在声明的事件数之后还有 32 B，本次保留为不透明尾部，未推断其含义。
种子、原始头、这 2 位以及尾部都要保留，不能只保存解析器提取出的字段。

### Clone 2006/2007

[C 解析器的 `read_2007`][mvf-c] 读取 6 B 记录，使用同类种子算法生成 48 位排列：

| 逻辑位 | 内容 |
| --- | --- |
| 0–2 | 右、中、左键状态 |
| 3–13 | y，11 位，解码后减 32 |
| 14–24 | x，11 位，解码后减 32 |
| 25–46 | 绝对毫秒，22 位 |
| 47 | 未使用位，必须保留 |

这不能套用 0.97 的 5 B 布局。种子运算依赖浮点数学函数和舍入，正式实现前还需要
跨平台检查排列生成的一致性，或直接将排列保存在预处理描述中，避免解压依赖浮点重算。
本地没有这个版本的真实样本；研究脚本中的分支只做合成/源码层面的覆盖。

### 0.96 及更早版本

[C 解析器的早期分支][mvf-c] 读取：`u8 秒 | u8 百分秒 | u8 buttons |
u16BE x | u16BE y | u8 未解释字段`，共 8 B。
状态字节低三位分别是左、中、右，与 0.97 的逻辑位顺序不同。
其余状态位和最后一个被上游命名为 `weirdness_bit` 的**字节**都不能丢弃。
版本判定依赖尾部校验、名字区和文件长度的启发式，本地尚无实测，扫描工具明确拒绝这些版本。

## RMV：混合事件流

文件以 `*rmv` 和 BE `u16` 版本号开头，头部有各段长度、`vid_size` 与校验段长度。
参见 [规格结构][rmv-structure]、[Rust 实现][rmv-rs]。
普通鼠标记录：

```text
type:u8 | t_ms:u24BE | nFlags:u8 | x:16BE | y:16BE   # 9 B
```

`1..7` 分别为 `mv lc lr rc rr mc mr`。`nFlags` 是鼠标/修饰键位标志：
`0x01` 左、`0x02` 右、`0x04` Shift、`0x08` Ctrl、`0x10` 中、`0x20/0x40` 侧键。
即使对扫雷操作无影响，也不能为了压缩而丢弃任何位。

RMV 1 的 x/y 是无符号窗口客户区坐标，转为棋盘坐标要分别减 `12`、`56`；
RMV 2 改成相对棋盘的有符号坐标。[C 实现][rmv-c] 没有完整落实 RMV 2 的符号/增量语义，
应以规格并结合 Rust 实现交叉检查，不能直接复用其 RAWVF 转换结果。

RMV 2 的类型 `28` 是 reduced mouse move：

```text
28:u8 | Δt_ms:u8 | (Δx:i4 << 4) | Δy:i4             # 3 B 总长
```

最后一字节的高/低半字节分别为 x/y 的补码增量，范围 `-8..7`。
位置、时间相对前一条鼠标记录，`nFlags` 沿用前值。适用条件是 `nFlags` 不变、
两轴增量在范围内、间隔不超过 255 ms。它已经是紧凑编码，不应先展开成 9 B 再丢弃原编码选择。

同一事件流还包含：

| 类型 | 载荷 | 总长 |
| --- | --- | --- |
| 0，仅 RMV 1 | `u32` timestampchange | 5 B |
| 9–14、18–27 | `u8 col, u8 row`，棋盘格状态更新，没有独立时间 | 3 B |
| 15/16/17 | 失败/胜利/其他结束；草案列出 `u24 time_ms` | 草案为 4 B，见下述实测差异 |

**实测与草案的差异：**222 个 RMV 1、1,463 个 RMV 2 样本的结束码都是 `16`，
结束码后到 `vid_size` 边界都有 **8 B**，而草案只解释其中前三个时间字节。
例如局部字节 `10 00 03 f3 00 00 00 03 f3`：`10` 是十六进制结束码，
后面 8 B 仍在视频段中，之后才到头部声明的校验段。
扫描器按草案读取 3 B，再把余下 **5 B** 记录为不透明视频尾部；未擅自赋予其语义。
生产实现不能假设结束码后固定只有 3 B，必须保留长度边界内的全部内容。

原始 1,463 份 RMV 2 共有 10,455,573 条鼠标记录，其中 9,854,239 条是类型 `28`
的 reduced move。这种布局应单独预处理：4 位有符号坐标增量做同宽 ZigZag，
普通鼠标坐标按 16 位模差分后 ZigZag，且 reduced move 必须更新后续普通记录的基准。
不能把 RMV 2 当作连续的 9 B 记录，也不能将已有的小增量再重复差分。

上游分析器还会根据预标旗生成 `pf`、补造初始 `lc`、忽略棋盘事件及 `nFlags`，
并改写越界坐标。这些行为适合回放分析，不适合直接重建原文件。

## EVF：0.3 与 0.4 的区别

文件首字节 `3/4` 对应英文规格的 EVF **0.3/0.4**；中文规格简称 **v3/v4**。
它们与 MSRC 容器版本、算法版本是不同概念。

### EVF 0.3：固定 8 B

[规格][evf-en] 与 [解析器][evf-rs]：

```text
type:u8 | t_ms:u24BE | x:u16BE | y:u16BE
```

时间是绝对毫秒，坐标相对棋盘边界。事件码 `1..7` 同 RMV；`8 pf`、`9 cc`、
`10 l`、`11 r`、`12 m` 中，`cc` 表示需要状态机解释的组合按下，
`l/r/m` 表示需要状态机确定方向的按键变化，并不携带完整按键快照。
不能把这些码规范化后丢弃原值。

`0` 终止事件流且后有 32 B 校验；`255` 终止且无校验。
EVF 0.0–0.2 在当前解析器中也使用这类 8 B 鼠标记录，但头字段和可用事件码不同，
不能仅按 8 B 宽度自动判定版本；本次扫描没有实现它们的头部。

### EVF 0.4：6 B 增量记录

[中文规格][evf-zh]、[读取器][evf-rs] 与 [写入器][evf-writer]：

```text
type:u8 | Δt_ms:u8 | Δx:i16BE | Δy:i16BE
```

坐标相对**上一条鼠标记录**；首条相对 `(0,0)`，因此其坐标数值就是起始位置。
时间相对**上一条有时间的事件**，不能只维护“上一条鼠标时间”。
`255 | Δt_ms:u16BE` 是 3 B pause，可连续出现，增量累加到后续事件。
例如间隔 1000 ms 可写 `ff 03 e8` 后接 `Δt=0` 的下一条鼠标记录；
不要在还原时重新选择另一种等价的 pause 拆分。

混合事件还包括：

| 类型 | 载荷 | 总长 |
| --- | --- | --- |
| 81/82/83/99 | `u8 Δt`，重开/胜利/失败/错误 | 2 B |
| 棋盘事件 100–199 中已定义的码 | 中文规格为 `u8 Δt, u8 row, u8 col` | 中文规格为 4 B |
| 200 | `u8 Δt, u16 指标索引+10000, f64 数值` | 12 B |
| 201 | `u8 Δt, u16 指标索引+10000, UTF-8 零结尾字符串` | 变长 |
| 255 | `u16 Δt` | 3 B |
| 0 | 无载荷，事件流结束，之后 `u16 校验长度 + 校验字节` | 1 B |

**尚未可靠覆盖的部分：**固定提交的英文规格把棋盘坐标写成“1 byte int16”增量 x/y，
中文规格则是各 1 B 的绝对 row/col，二者不一致。
Rust 读取器对 `100..199`、`200..254` 的分支为空，未消费载荷，无法解决这一分歧；
写入器目前只输出鼠标事件和 pause。因此不能用这套解析器证明完整的混合事件支持。
本地实测 498 份 EVF 0.4 只出现鼠标、pause、结束标记；扫描器遇到棋盘/指标事件会报错，
正式算法应保持原文或回退，直到有真实样本和明确的写入实现可核对。

## EVFS：多个完整 EVF 的封装

[规格][evfs-spec] 与 [实现][evfs-rs]：

```text
version:u8 = 0
unit_checksum_length:u16BE
repeat until EOF:
    filename:UTF-8 + NUL
    evf_length:u32BE
    evf_bytes[evf_length]
    unit_checksum[unit_checksum_length]
```

所以 `.evfs` 的首字节 `0` 已可确认为 **EVFS 0.0**，不能当作单份 EVF 0.0。
集合级的单元校验与 EVF 自己的校验是两层数据，都要保留。
本地 6 个 EVFS 共含 298 个完整 EVF 0.4；每个 EVF 应独立初始化时间、坐标基线。
文件名、顺序、单元边界不能因合并事件流而丢失。

## RAWVF：文本转换格式

[项目说明][raw] 与 [AVF 的 RAWVF 输出][avf-c] 显示，常见鼠标行为：

```text
Events:
1.230 mv 2 3 (19 38)
```

依次是秒、事件名、格坐标、括号内像素坐标；此例是从 1 开始的格坐标、16 像素格。
文本还可能含额外棋盘事件、统计、不同精度、空白与换行。若未来对 RAWVF 预处理，
必须把这些词法信息一起保存，不能只对数值重新排版。
原生格式转 RAWVF 常会丢弃冗余鼠标移动、合并 AVF 别名、展开 MVF 状态、补造事件，
因此“转 RAWVF 再压缩”不能保证恢复原生文件字节。

没有把上游完整分析器引入生产依赖。输出文件被 Git 忽略：

| --- | ---: | ---: | ---: | ---: |
| AVF | 304 | 1,140,807 | 98.607% | 99.912% |
| MVF 0.97 | 6 | 13,317 | 97.656% | 98.813% |
| RMV 1 | 222 | 602,038 | 94.936% | 99.989% |

最后一列的分母是每份录像内的相邻鼠标记录对，首条不计；包含点击和移动，
忽略是否可以省略按键状态，所以**不是 RMV reduced move 的可用率或压缩率**。

所有已扫描鼠标时间均未倒退，但算法仍须能保留异常时间和值域，不能以此为依据丢弃信息。

## 已实现的 V2 方案

1. **AVF、RMV 1、EVF 0.3：字段分流 + 整数差分 + LZMA。**
   把事件码、时间、x/y、额外字段分开，解除 AVF 的交错；时间保持原位宽做模差分，
   坐标保持原位宽做模差分与 ZigZag。无法可靠识别的输入保留原始字节路径。
2. **EVF 0.4、RMV 2 reduced move：增量字段分流与 ZigZag。**
   原格式已经差分，不再重复差分；分别对 16 位和 4 位有符号坐标增量做 ZigZag。
   保留 pause 的数量、载荷和位置，不按语义重新生成它们。
3. **MVF 0.97：解除位重排后，分离状态、时间、坐标和残余位。**
   这 6 个样本已验证逐位还原；残余位完整保留，位排列写入描述，解压无需浮点重算。
   2006/2007、早期 MVF 需要各自样本，不能直接扩展结论。
4. **EVFS：保留单元边界，在完整集合上比较压缩。**
   共享 LZMA 上下文利用重复头信息，同时保存每个单元的原始名字、长度、校验与 EVF 字节。

V2 使用独立的算法版本号 `(1, 2)`，默认启用，并保留 V1 `(1, 1)` 的压缩器和解压器。
对原始字节与预处理结果分别运行 LZMA，选择包含描述开销后较小的载荷。
[benchmark](../../benchmarks/README.md) 记录分格式的完整容器大小和压缩/解压吞吐量；
本次未测量峰值内存，不能据此推断实际进程内存占用。
